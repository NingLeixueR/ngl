# NGL 框架客观评价

> 本文用于在私有仓库无法直接公开源码的情况下，对外概括介绍 NGL 框架。评价基于当前源码、CMake/Conan 配置、Actor 调度实现、网络缓冲池、测试结构和项目文档，重点放在架构设计、C++ 现代性、代码质量、工程化构建与依赖管理等维度。

## 框架简介

NGL 是一个基于 C++23 的游戏服务端框架，核心采用 Actor 模型组织业务逻辑，面向长连接、多节点、分区分服、实时消息路由等在线游戏后端场景。

框架覆盖的主要能力包括：

- Actor 驱动的业务模块组织方式。
- 多节点服务启动与区服配置。
- TCP、WebSocket、KCP/UDP 三协议网络栈。
- Protobuf、自定义协议、XML、CSV 配置体系。
- MySQL、PostgreSQL、Redis 数据后端封装。
- 网关转发、跨节点 Actor 通信、客户端消息路由。
- GM/运营后台。
- GoogleTest/CTest 测试体系。

从整体定位看，NGL 更接近一个中小型在线游戏服务端基础框架，而不是普通 Web 服务框架。它关注的是游戏后端常见问题，例如长连接接入、角色状态管理、消息分发、网关转发、配置热更新、排行榜、邮件、聊天、活动、家族、背包和任务等。

## 架构设计

**得分：8.0 / 10**

NGL 的架构核心是 Actor 模型。不同业务模块被封装为独立 Actor，Actor 之间通过异步消息通信，减少共享状态和业务层显式加锁。每个 Actor 使用 64 位 ID 标识，其中包含 Actor 类型、区服 ID 和实例 ID，适合游戏后端的单例服务、动态角色对象、分服寻址和跨节点通信。

### Actor 分层调度

框架没有把所有 Actor 放进一个全局队列中调度，而是将 Actor 分散到多个 `schedule_layer` 中。`actor_manage` 中固定使用 8 个调度层，层索引通过位掩码计算：单例 Actor 按 Actor 类型分层，动态 Actor 按实例 ID 分层。每个调度层维护自己的 Actor 查找表、就绪队列和调度线程，全局 `actor_manage` 再维护共享工作线程池。

这种设计的价值在于：

- 降低全局队列和全局锁竞争。
- 提高大量 Actor 并存时的并行调度能力。
- 通过共享工作线程池控制线程总量。
- 避免热点 Actor 或大量角色 Actor 集中在单一调度层。

Actor 内部区分普通消息队列和高优先级消息队列。协议注册时可以为消息配置优先级，高优先级消息按优先级值分桶存储，普通消息进入 FIFO 队列。`actor_handle` 执行时会先处理高优先级桶，再处理普通队列。

普通消息处理带有权重和软时间预算，用于限制单次调度处理量，避免某个 Actor 因消息积压长期占用工作线程。代码中还采用 swap 到本地队列的方式处理消息，使 handler 执行期间新消息入队不必长期持有 Actor 锁。

**客观评价：**

Actor 分层调度、高优先级消息队列、调度切片控制和本地队列 swap，是 NGL 中比较有深度的设计点。它比简单的“线程池 + 全局任务队列”更适合大量游戏对象并存的场景。

不足是调度体系复杂度较高。调度线程当前采用 detach 且进程生命周期常驻策略，优雅退出、停机排空和线程 join 不是设计重点。后续如果要更接近生产级，需要补充 Actor 队列长度、调度耗时、工作线程占用率、消息延迟分位数等指标，否则定位慢 Actor 或消息积压会比较依赖日志和经验。

### 三协议网络栈

NGL 支持 TCP、WebSocket 和 KCP/UDP 三类传输方式：

| 协议 | 典型场景 |
|------|----------|
| TCP | 服务器间通信、传统客户端连接 |
| WebSocket | 浏览器客户端、Web 环境 |
| KCP/UDP | 低延迟实时通信 |

网络层通过统一门面向上提供发送接口，业务层不需要直接关心底层传输类型。客户端消息可以经过网关进入 Actor 系统，服务端响应也可以通过网关回到客户端。

框架还包含心跳、超时、限速、包重组、session 管理等长连接基础能力。TCP 流式数据通过 `segpack` 重组完整包，网络消息通过 `pack` 结构统一承载协议号、Actor ID、包头和包体。`pack` 明确禁用拷贝，避免拥有裸缓冲指针时发生浅拷贝和 double-free。

**客观评价：**

三协议网络栈覆盖面较广，符合游戏服务端对不同客户端形态和实时性的需求。TCP、WebSocket、KCP 同时存在，说明框架不是只面向单一连接模型。`pack`、`segpack`、限速标记和 session 映射这些基础设施也说明网络层不是简单封装 socket。

不足是网络抽象的一致性仍可继续提升。三类传输虽然向上统一，但底层连接状态、错误处理、重连、限速、安全鉴权和观测指标仍需要进一步标准化。

### 节点与业务模块

NGL 使用统一 `node` 入口，通过启动参数和配置装配成不同节点，例如 DB、GAME、GATEWAY、LOGIN、WORLD、LOG、ROBOT、CROSS 等。不同节点承担不同职责，符合游戏服务端常见的多进程、多节点运行模型。

业务模块上，框架已经覆盖登录、网关、角色、聊天、邮件、排行榜、家族、活动、机器人、GM 等常见游戏服务端模块。角色业务下还包含背包、道具、任务、属性、地图/AOI 等领域模块。

**客观评价：**

整体架构覆盖面较完整，能体现对游戏服务端链路的理解。缺点是模块数量较多，Actor、协议、DB、配置、生成链路之间存在较多约定，新成员上手成本较高。

## C++ 现代性

**得分：7.5 / 10**

NGL 使用 C++23 标准，整体代码偏现代 C++ 风格。框架中大量使用模板、智能指针、RAII、类型注册、类型擦除、静态单例、泛型 DB client、泛型协议注册等机制。

### 现代 C++ 使用情况

比较明显的现代 C++ 特征包括：

- 使用 C++23 标准构建。
- 以 `std::shared_ptr` / `std::unique_ptr` 管理大量 Actor、线程和组件对象。
- 使用 `std::optional` 表达高优先级就绪状态、KCP 端口查找等可选结果。
- 使用 `std::format` 统一格式化日志和运行时名称。
- 局部使用 `std::ranges` 处理文本转换和工具逻辑。
- 在时间轮等工具中使用 `std::jthread`。
- 使用模板实现协议注册、Actor handler 注册、DB client 和 CSV 表封装。
- 使用类型擦除承载消息信封和通用分发。
- 使用 RAII 辅助类处理调度挂起等作用域状态。
- 使用标准库容器组织 Actor 表、消息队列、协议表和配置表。
- 构建层面支持 sanitizer、unity build、mimalloc 等现代工程选项。

### 模板与类型系统

协议注册、Actor 消息分发、DB 组件和 CSV 表封装都大量依赖模板。这样可以减少重复代码，让业务层以类型化方式注册 handler、读取配置、操作 DB 组件。

这类设计的优势是：

- 编译期类型约束更强。
- 业务代码不需要大量手写 switch-case。
- 协议和 handler 的关系更清晰。
- DB 表、CSV 表可以以类型化方式访问。

**客观评价：**

模板和类型系统运用比较熟练，说明框架并不是传统 C 风格的 C++ 项目。类型化协议、Actor handler 注册、泛型 DB client 这些设计有一定复杂度，也能体现作者对现代 C++ 抽象能力的掌握。

不足是当前现代性主要体现在模板、智能指针和常用标准库设施上。C++20/23 中更进一步的 concepts、coroutine、module 等特性基本没有形成框架级应用。尤其是网络 IO 和异步流程仍主要依赖传统 callback、Actor 消息和线程模型，没有使用 coroutine 重塑异步表达。

### 内存分配相关现代性

框架支持可选启用 mimalloc，并在网络包上使用缓冲池减少频繁分配。`socket_pool` 是线程本地缓存 + 按桶跨线程归还队列 + 统计快照的设计，`pack` 结构保留缓冲池反向指针，便于统一管理网络消息生命周期。

**客观评价：**

这体现了对 C++ 服务端内存分配成本的关注。mimalloc、线程本地桶缓存和 `pack` 生命周期管理在高频消息场景下有实际价值，但仍需要通过分配次数、内存峰值、碎片率、缓冲池命中率等指标证明收益。

## 代码质量

**得分：7.0 / 10**

NGL 的代码质量整体处于可维护但仍有明显改进空间的状态。核心层较多对象显式禁用拷贝，RAII 和组件化意识较强，模块边界也有一定划分。但由于框架复杂度较高，仍存在生命周期、线程退出、状态机边界和安全治理方面的隐患。

### 正向质量表现

比较正向的代码质量表现包括：

- Actor、网络、DB、配置、协议、工具层职责基本清晰。
- 核心对象多使用智能指针和容器管理。
- `pack` 这类拥有裸缓冲区的对象显式禁用拷贝，避免浅拷贝导致 double-free。
- `socket_pool` 带有魔数校验、线程槽位和桶级统计，说明内存池不是无保护裸分配。
- Actor 调度、DB client、协议注册等模块有较强组件化意识。
- 测试覆盖运行时、网络、序列化、配置、Actor 管理、socket pool、过滤词等关键基础设施。
- 文档覆盖 Actor 架构、消息流、网络层、数据库层、配置系统等主要模块。
- 构建配置中保留 sanitizer 选项，有利于发现内存和未定义行为问题。

### 内存与资源管理

框架在网络包和 Actor 对象生命周期上做了较多封装。网络消息由 `pack` 承载，配合缓冲池降低重复分配；Actor 由调度层和 `actor_manage` 统一管理；DB 数据通过组件和脏标记机制管理。

**客观评价：**

核心层没有明显大量随意裸指针释放的风格，整体不是低质量堆砌。需要区分的是：Demo、工具和第三方 KCP 中仍能看到不少 `new/delete/malloc/free`；框架核心里的裸缓冲更多是网络包和内存池的有意设计。部分对象采用进程生命周期常驻策略，线程析构和优雅退出没有完全工程化，这在长驻游戏进程中可以理解，但仍是代码质量边界问题。

### 状态机与生命周期风险

Actor 系统涉及 init、free、list、run、close 等状态变化，调度层、工作线程、消息队列、延迟删除、广播 tick、DB 刷盘之间存在复杂交互。

潜在风险包括：

- Actor 关闭过程中仍有消息进入。
- 调度线程长期 detach，缺少完整 stop/join/drain 流程。
- 高优先级消息使用不当可能导致普通消息饥饿。
- DB 批量刷盘存在数据丢失窗口。
- CSV 热更新依赖调度挂起，异常路径需要严格处理。

**客观评价：**

这些问题并不说明框架不可用，而是说明它已经进入复杂服务端框架常见的生命周期治理阶段。后续质量提升的重点应是状态机边界、线程退出、异常路径、指标监控和自动化测试。

### 安全质量

GM 后台和管理通道存在较明显安全短板，例如旧 PHP `mysql_*` 扩展、MD5 密码、管理 Socket 鉴权不足、输入校验不足、XOR 不能替代正式加密等。

**客观评价：**

安全性是当前代码质量中比较明显的扣分项。作为内网验证和开发工具可以接受，但生产化需要重点改造认证、权限、传输加密、输入校验和审计。

## 工程化（构建/依赖）

**得分：8.5 / 10**

NGL 的工程化配套相对完整，尤其是在构建、依赖管理、测试和构建选项方面。

### 构建体系

项目使用 CMake，并采用 target-based 的组织方式。核心库、节点入口、测试目标、工具目标之间有明确划分。构建选项包括：

- C++23 标准。
- 强编译告警选项。
- AddressSanitizer / UndefinedBehaviorSanitizer 开关。
- native unity build 和 unity batch size。
- mimalloc 开关，并通过单独 `mi_new.cpp` 接入全局 new/delete。
- 静态/动态核心库构建选项。
- 测试构建开关。
- 性能测试注册开关。

**客观评价：**

CMake 配置比较成熟，不是简单的文件列表式构建。`ngl_build_options`、运行时依赖应用函数、mimalloc 注入函数、sanitizer 函数、unity build 分组函数都体现了工程化封装意识。

### 依赖管理

项目使用 Conan 管理第三方依赖，并对主要依赖版本进行 pin。依赖包括 Boost、behaviortree.cpp、tinyxml2、Lua、Protobuf、libcurl、MySQL client、hiredis、libpq、rapidjson、mimalloc、GoogleTest 等。Windows 下还引入 SDL 和 ImGui，用于本地 Demo/工具侧能力。

**客观评价：**

Conan 全 pin 能提升可复现性，适合私有 C++ 服务端项目长期维护。相比手工管理第三方库，这种方式更工程化，也更容易迁移构建环境。

### 测试体系

测试使用 GoogleTest，并通过 CTest 注册。当前测试文件包括 Actor 管理、角色、启动、网络、过滤词、性能、运行时、序列化、smoke、socket pool、工具函数和 XML 系统配置等方向。普通 fast 测试和性能测试分离，性能测试需要显式开启。

**客观评价：**

测试体系已经具备基础规模，不是完全依赖手工验证。fast/perf 分离比较合理。缺点是复杂游戏服务端还需要更强的跨节点集成测试、稳定性测试、压力测试和故障注入测试。

### 文档与模块说明

仓库中已有较多文档，覆盖目录结构、Actor 架构、消息流、网络层、数据库层、配置系统、网关架构、测试模块、GM 后台、新增 Actor 指南等内容。

**客观评价：**

文档覆盖面较好，有利于私有框架对外说明和团队内部交接。后续还可以补充更直观的架构图、链路图、指标说明、故障排查流程和生成链路说明。

## 主要优势

- 架构领域针对性强，围绕游戏服务端常见问题设计。
- Actor 分层调度、高优先级队列、调度切片、本地队列 swap 等机制具备一定深度。
- TCP、WebSocket、KCP 三协议网络栈覆盖不同客户端和实时通信场景。
- 线程本地 socket 缓冲池、pack 禁拷贝、mimalloc、DB 脏标记和批量刷盘体现性能优化意识。
- C++ 模板、类型注册、泛型 DB client、CSV 类型封装等抽象能力较强。
- CMake、Conan、GoogleTest、CTest、sanitizer、unity build、依赖 pin 等工程配套较完整。
- 文档覆盖面较好，便于说明框架结构和模块边界。

## 主要不足

- Actor 调度、缓冲池、DB 刷盘等优化机制还缺少系统压测和指标数据支撑。
- 调度体系复杂度较高，需要更完善的可观测性。
- C++ 现代特性使用集中在模板、智能指针和常用标准库设施，concepts/coroutine/module 等特性没有形成框架级应用。
- 部分线程和对象采用进程生命周期常驻策略，优雅退出和资源回收流程不够完整。
- 高优先级消息、Actor 状态机、延迟删除、DB 刷盘等边界路径需要更强测试覆盖。
- GM 后台和管理通道安全性偏弱。
- 生成链路和注册约定较多，新成员上手成本较高。
