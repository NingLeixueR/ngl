# NGL 框架客观评价

> 本文用于在私有仓库无法直接公开源码的情况下，向面试官或新团队概括介绍 NGL 框架。内容按框架简介、性能、扩展性、工程化、安全性等维度进行评价，并给出相对客观的评分。

## 1. 框架简介

NGL 是一个基于 C++23 的游戏服务端框架，核心采用 Actor 模型组织业务逻辑，面向长连接、多节点、分区分服、实时消息路由等在线游戏后端场景。

框架覆盖的主要能力包括：

- Actor 驱动的业务模块组织方式
- 多节点服务启动与区服配置
- TCP、WebSocket、KCP/UDP 网络接入
- Protobuf、自定义协议、XML、CSV 配置体系
- MySQL、PostgreSQL、Redis 数据后端封装
- 网关转发、跨节点 Actor 通信、客户端消息路由
- GM/运营后台
- GoogleTest/CTest 测试体系

从整体定位看，NGL 更接近一个中小型在线游戏服务端基础框架，而不是普通 Web 服务框架。它关注的是游戏后端常见问题，例如长连接接入、角色状态管理、消息分发、网关转发、配置热更新、排行榜、邮件、聊天、活动、家族、背包和任务等。

**客观评价：**

NGL 的定位比较清晰，能够体现作者在 C++ 服务端、游戏后端、网络通信、多线程调度、协议系统、数据库持久化和工程化方面的综合能力。它适合被介绍为“个人或小团队沉淀的游戏服务端框架”，不应直接描述为已经完全成熟的大规模商业生产平台。

**评分：8.0 / 10**

## 2. 架构设计

NGL 的核心架构基于 Actor 模型。不同业务模块被封装为独立 Actor，Actor 之间通过异步消息通信，尽量减少共享状态和业务层显式加锁。

框架使用 64 位 Actor ID 表示 Actor 身份，其中包含 Actor 类型、区服 ID 和实例 ID。这种设计适合游戏后端的分服、分区、单例服务、动态角色对象和跨节点寻址。

服务启动方面，NGL 使用统一 `node` 入口，通过启动参数和配置装配成不同节点，例如 DB、GAME、GATEWAY、LOGIN、WORLD、LOG、ROBOT、CROSS 等。不同节点承担不同职责，符合游戏服务端常见的多进程、多节点运行模型。

Actor 调度方面，框架使用分层调度和共享工作线程池。动态 Actor 可以按实例 ID 分散到不同调度层，降低单点队列压力。消息队列区分普通消息和高优先级消息，关键控制类消息可以优先处理。

**客观评价：**

架构设计有较强的领域针对性。Actor 模型、网关转发、DB Actor、区服 ID、多节点启动等设计都符合游戏服务端实际场景。相比普通业务服务器，它更关注长连接状态、消息路由、角色对象生命周期和跨节点协作。

不足是架构复杂度较高。Actor 调度、协议注册、跨节点转发、数据库组件和生成链路之间存在较多协作关系，新成员理解成本不低。若用于团队项目，需要更完善的架构图、开发规范和故障排查文档。

**评分：8.0 / 10**

## 3. 性能

NGL 在性能方面有多处设计：

- Actor 模型减少业务层共享状态。
- 多调度层分散 Actor 队列压力。
- 共享工作线程池控制线程数量。
- 高优先级消息队列保障关键消息处理。
- TCP 包重组处理粘包和拆包。
- 网络包缓冲池减少频繁内存分配。
- 支持 mimalloc 优化内存分配。
- 支持 KCP/UDP 以适配低延迟实时通信。
- GoogleTest 中保留性能测试入口，普通测试和性能测试分离。

这些设计说明框架对游戏服务端常见性能问题有明确意识，例如消息积压、网络包分配、长连接数据分片、Actor 并行度、关键消息优先级和实时通信延迟。

**客观评价：**

NGL 具备较好的性能设计基础，但目前更准确的评价是“有性能优化意识和基础机制”，而不是“已被大规模生产验证的高性能框架”。如果要证明生产级性能，还需要补充压测报告、吞吐量数据、延迟分位数、Actor 队列长度、DB 请求耗时、网络丢包和重传等量化指标。

**评分：7.0 / 10**

## 4. 扩展性

NGL 的扩展性体现在多个方面：

- 新增业务可以通过新增 Actor 实现。
- 协议通过注册表和生成链路维护。
- 节点可按类型装配，不同节点启动不同 Actor 集合。
- CSV 表支持类型化封装，便于扩展策划数据。
- DB 组件可以挂载到 Actor 上，支持不同表数据的加载和保存。
- 网络层通过统一门面屏蔽 TCP、WebSocket、KCP 差异。
- IDL 和 makeproto 工具支持协议、数据库、客户端代码等辅助产物生成。

**客观评价：**

框架的扩展路径比较清晰，适合逐步增加业务 Actor、协议和配置表。对游戏项目中常见的“新增玩法服务”“新增公共服务”“新增协议”“新增策划表”都有基本路径。

不足是扩展链路依赖 C++ 模板、生成代码和框架约定。如果自动化脚本、CI 校验和新模块开发指南不够完善，容易出现漏注册、漏生成、协议不一致等问题。

**评分：7.5 / 10**

## 5. 网络通信

NGL 支持 TCP、WebSocket 和 KCP/UDP 三类传输方式：

| 传输方式 | 适用场景 |
|----------|----------|
| TCP | 服务器间通信、传统客户端连接 |
| WebSocket | 浏览器客户端、Web 环境 |
| KCP/UDP | 低延迟实时通信 |

网络层通过统一门面向上提供发送接口，业务层不需要直接关心底层传输类型。客户端消息可以经过网关进入 Actor 系统，服务端响应也可以通过网关回到客户端。

框架还包含心跳、超时、限速、包重组、session 管理等长连接基础能力。

**客观评价：**

网络层覆盖面较广，能够体现作者对游戏长连接服务的理解。TCP、WebSocket、KCP 同时支持，对不同客户端形态和实时性场景都有考虑。

不足是生产级网络安全和观测能力还需要加强。例如 XOR 只能视为简单混淆，不能替代正式加密；限速、异常连接、丢包、重传、延迟等指标需要系统化监控。

**评分：7.5 / 10**

## 6. 数据持久化

NGL 的数据库层采用 Actor 化思路。业务 Actor 不直接阻塞访问数据库，而是通过 DB Actor 和 DB client 进行加载、保存和删除。数据修改通过脏标记记录，再进行批量保存。

框架支持 MySQL、PostgreSQL 和 Redis，适合角色数据、背包数据、排行榜数据、家族数据等游戏状态型数据。

**客观评价：**

数据库设计符合游戏服务端常见实践，重点在异步化、组件化和批量保存。它可以体现作者对“角色状态常驻内存、周期性落库、减少同步 DB 阻塞”的理解。

不足是强一致性、跨表事务、失败重试、幂等处理和崩溃恢复策略还需要进一步完善。当前设计更适合游戏状态持久化，不适合直接承担强事务要求很高的业务系统。

**评分：7.0 / 10**

## 7. 配置与热更新

NGL 使用 XML 管理运行时系统配置，使用 CSV 管理游戏策划数据。CSV 表通过类型化封装供业务读取，并支持校验和热更新机制。

配置内容覆盖服务器列表、网络参数、日志参数、KCP 参数、限速参数、开服时间、活动、道具、任务、地图、聊天、邮件等多个方面。

**客观评价：**

配置体系符合游戏项目常见工作流，尤其适合“策划表 + 服务端类型封装 + 热更新”的开发模式。

不足是热更新本身风险较高，需要严格校验表结构、字段合法性、引用关系和回滚能力。当前更像是具备热更新基础能力，距离完整配置发布平台还需要补充灰度、审批、校验、回滚和变更审计。

**评分：7.0 / 10**

## 8. 工程化

NGL 的工程化配套包括：

- CMake 构建体系
- Conan 依赖管理
- GoogleTest 单元测试和回归测试
- CTest 集成
- 性能测试与普通测试分离
- GitHub Actions CI 标识
- SonarCloud 质量门禁标识
- 模块化文档
- PHP GM 后台工具

**客观评价：**

工程化意识较强。对于个人项目或小团队私有框架来说，能同时具备构建、依赖管理、测试、文档和后台工具，是比较有说服力的。

不足是还需要更完整的自动化生成流程、统一日志与指标采集、CI 中的协议一致性校验、测试覆盖率统计、压测报告和代码规范检查。

**评分：8.0 / 10**

## 9. 安全性

NGL 在服务端主体上提供了基础网络限速、心跳、超时和简单包体混淆能力。GM 后台也包含登录、权限和操作日志功能。

但从当前设计看，安全性仍是明显短板：

- GM 后台存在旧版 PHP `mysql_*` 扩展问题。
- 密码使用 MD5，不符合现代安全要求。
- GM Socket 通信缺少强鉴权握手。
- 输入参数校验需要加强。
- 配置中存在硬编码敏感信息的风险。
- XOR 混淆不能替代 TLS 或正式加密。

**客观评价：**

安全能力目前更适合作为开发验证和内网工具使用，不应直接暴露到公网生产环境。若要生产化，应优先改造 GM 后台认证、权限、密码存储、接口鉴权、传输加密、输入校验和审计能力。

**评分：5.5 / 10**

## 10. 测试质量

NGL 使用 GoogleTest，测试覆盖运行时、网络、序列化、配置、Actor 管理、Socket pool、过滤词、性能基准等方向。测试文件通过 CMake 自动收集，默认 fast 测试和性能测试分离。

**客观评价：**

测试体系已经具备基础规模，不是完全依赖手工测试。fast 测试和 perf 测试分离也比较合理。

不足是复杂游戏服务端还需要更强的集成测试、跨节点测试、长时间稳定性测试、压力测试和故障注入测试。现有测试能证明作者有测试意识，但还不能完全证明框架经过大规模线上压力验证。

**评分：7.0 / 10**

## 11. 文档质量

仓库中已有较多文档，覆盖目录结构、Actor 架构、消息流、网络层、数据库层、配置系统、网关架构、测试模块、GM 后台、新增 Actor 指南等内容。

**客观评价：**

文档覆盖面较好，对私有仓库求职展示很有帮助。它能让面试官在看不到源码的情况下理解项目边界、设计思路和复杂度。

不足是部分文档仍偏模块说明。若用于团队协作，还需要增加更直观的架构图、链路图、故障排查流程、开发规范、协议生成流程和上线流程。

**评分：8.0 / 10**

综合来看，NGL 是一个完成度较高的 C++ 游戏服务端框架。它能够体现作者在游戏后端架构、Actor 并发模型、长连接网络、协议系统、数据库持久化、配置管理、测试体系和运营工具方面的综合能力。

从求职展示角度看，它的价值较高，适合作为核心项目介绍。从框架成熟度角度看，它仍需要更多压测数据、监控指标、安全改造和团队化工程规范支撑。

## 13. 主要优势

- 领域针对性强，围绕游戏服务端常见问题设计。
- 架构完整度较高，覆盖 Actor、网络、协议、DB、配置、后台、测试。
- 并发模型明确，使用 Actor 和消息队列降低共享状态复杂度。
- 网络能力较丰富，支持 TCP、WebSocket、KCP。
- 扩展路径清晰，新增 Actor、协议、配置表和节点都有基本路径。
- 工程化意识较强，包含 CMake、Conan、GoogleTest、CI、文档。
- 适合求职展示，能体现 C++ 游戏服务端综合能力。

## 14. 主要不足

- 生产级可观测性不足，缺少完整指标体系和压测数据。
- 安全体系偏弱，尤其是 GM 后台和管理通道。
- 优雅退出、线程停止、资源释放流程不够完整。
- 协议和代码生成链路较复杂，需要更强自动化和规范。
- C++ 模板、Actor 注册、生成代码结合较多，新人上手成本较高。
- 数据库层更偏游戏状态持久化，不适合直接承担强事务系统。
- 框架成熟度还需要线上运行数据、稳定性测试和团队协作验证支撑。
