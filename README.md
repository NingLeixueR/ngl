# ngl_server 框架技术分析

> 一个基于 Actor 模型的分布式 C++ 游戏服务器框架的客观技术评估
>
> 本文档从架构设计、C++ 现代性、代码质量、工程化四个维度对框架进行评分与分析,
> 评估基于对源码的全量阅读(约 17 万行项目代码,不含第三方库与生成代码)。

---

## 一句话定位

`ngl_server` 是一个面向多人在线游戏服务端、以 **Actor 模型**为并发内核、以**单二进制多角色**为部署形态的分布式 C++20 框架,自带网络栈(TCP/WebSocket/KCP)、序列化、异步日志、数据库访问层、Lua 脚本与行为树等完整基础设施。

## 一、架构设计 —— 8.0 / 10

### 1.1 Actor 并发模型

框架以 Actor 模型作为并发内核,采用**两层调度架构**:

- **schedule_layer(调度层)**:若干独立调度单元,各自持有互斥锁与调度线程,负责把就绪的 actor 投递给工作线程。
- **actor_manage(路由层)**:单例,管理共享工作线程池,按 `dataid`/`type` 对 actor 进行路由分散,均衡负载。

消息分发使用**双优先级队列**(普通 FIFO + 高优先级分桶),支持动态 actor、单例 actor、广播机制与脚本扩展。actor 的创建通过模板工厂 `actor_base::create<TACTOR>` 完成,消息处理器注册使用 C++17 折叠表达式 `register_handle<T, ARG...>`,写法现代且类型安全。

**设计亮点**
- 分层隔离显著降低锁竞争,工作线程池与调度逻辑解耦。
- 路由按数据/类型分散,具备水平扩展基础。
- 优先级队列让实时性业务(如战斗)可抢占普通业务。

### 1.2 分布式拓扑:单二进制多角色

这是该框架在架构上最具实用价值的设计之一。整个服务端只有**一个可执行文件 `node`**,启动方式为:

```
node <节点名> <区area> <tcount>
```

进程启动后,从 `tab_servers.csv` 反查该节点的类型,装载对应的 actor 集合(见 `server_main.cpp` 的 `switch(nodetype())` 分发)。这意味着:

- **一套代码、一个镜像**即可扮演 12 种节点角色,差异完全由启动参数与配置表驱动。
- 节点的网络布局、线程数、依赖关系全部由 `tab_servers.csv` 这一张表集中描述,运维视角清晰。
- 多区(area)与跨服(cross)在表结构层面就被一等公民地建模。

这种"配置即拓扑"的设计,使框架的部署形态非常适合容器化与水平伸缩。

### 1.3 网络栈

基于 **Boost.Asio(proactor 模式)** 与 **Boost.Beast(WebSocket)**,统一支持三种协议:

- **TCP**:面向内网节点互联与可靠长连接。
- **WebSocket / WSS**:面向 H5/Web 客户端,内置 TLS 证书链配置。
- **KCP**:面向弱网/移动端的低延迟可靠 UDP。

线程模型上,框架为每个会话分配独立 `io_context` 并绑定工作线程,以此规避显式 strand 的复杂度;发送路径采用 `const_buffer` 数组直接转发包头与包体,实现**零拷贝发送**,并用双缓冲(ping-pong)避免异步操作期间缓冲被覆盖。粘包/拆包下放给上层回调,网络层只负责字节流。

### 1.4 架构优缺点

**优点**
1. Actor 分层调度 + 路由分散,业务与基础设施解耦,扩展性好。
2. 单镜像多角色 + 配置驱动拓扑,部署模型干净,天然亲和容器编排。
3. 网络层零拷贝发送、双缓冲、按会话单线程串行写,性能与正确性兼顾。
4. 多区/跨服在数据模型层就被建模,不是事后补丁。

**待改进**
1. 三种网络协议缺少统一的顶层连接抽象——TCP/WS 共享继承链,KCP 走独立实现路径,接口未完全收敛。
2. 节点发现是**静态 IP 绑定**(网络层只解析 IP 字面量、不做 DNS 解析),在 Kubernetes 等动态环境中需要额外适配层。
3. 缺少优雅关闭机制:进程仅处理崩溃类信号(SIGSEGV/SIGABRT),未处理 SIGTERM/SIGINT,无法在收到停止信号时排空 actor、刷盘数据库。

> **架构评分 8.0**:扣分主要在协议抽象一致性、动态服务发现与优雅关闭这三处工程成熟度,而非设计思路本身。核心模型(Actor 分层 + 配置驱动拓扑)是成熟且经得起推敲的。

## 二、C++ 现代性 —— 7.5 / 10

### 2.1 已充分运用的现代特性

| 特性 | 运用情况 |
|------|----------|
| C++20 标准 | `CMAKE_CXX_STANDARD 20` + `STANDARD_REQUIRED ON`,强制达标 |
| 智能指针 | `shared_ptr`/`unique_ptr` 为主,连接对象 `enable_shared_from_this`,所有权清晰 |
| 折叠表达式 | 协议注册、序列化批量处理大量使用,代码简洁 |
| `std::formatter` 特化 | 为 map/vector/list 等容器自定义格式化,日志可读性强 |
| `std::jthread` | 用于 KCP 等独立线程,自动 join,异常安全 |
| `std::optional` | 用于可空返回值,减少裸指针语义歧义 |
| `std::shared_mutex` | 读写锁分离,连接表等读多写少场景 |
| 模板元编程 | 类型安全的 actor 工厂、协议号映射、序列化反射 |

整体可以看出作者对模板元编程与现代 C++ 资源管理有扎实掌握,不是"C with classes"风格。

### 2.2 尚未释放的现代化红利

- **concepts**:模板入口(如 `register_handle`、`create<TACTOR>`、序列化)仍依赖 SFINAE 与文档约束,未用 concepts。引入后可大幅改善编译错误信息与接口可读性,是性价比最高的升级点。
- **协程**:网络层仍是异步回调链,未采用 C++20 协程。引入协程可显著简化连接生命周期与异步组合逻辑。
- **module**:仍是传统 `#include`,大型头文件(如 protobuf 生成码)对编译时间有压力——这也是项目启用 Unity Build 的原因之一。
- **`<=>` 三向比较**:未使用。

### 2.3 C++23 升级准备

值得一提的是,项目已为 C++23 升级做了**完整的工程准备**:`CMakeLists.txt` 标准号、Conan `compiler.cppstd`、CI 缓存 key 均已参数化协同,并补充了编译器版本探测步骤。全量扫描确认代码未使用任何 C++23 移除/弃用特性(`aligned_storage`、`result_of`、`is_pod` 等均无命中),升级风险点集中在依赖重编译与自定义 `formatter` 的规则收紧,属可控范围。这反映出作者对语言演进有前瞻意识。

> **现代性评分 7.5**:扣分在 concepts/协程/module 这些 C++20 后期特性尚未落地;加分在已用特性运用得当,且对 C++23 演进有清晰规划。

## 三、代码质量 —— 7.2 / 10

### 3.1 内存管理:核心层纪律严明(重要正面信号)

对项目级源码(排除生成代码与 third_party)统计裸 `new`/`delete` 的分布,结论很能说明问题:

| 区域 | 裸内存分配情况 |
|------|----------------|
| 核心运行时(actor / net / libnglcore) | **几乎为零** |
| 演示代码(server/demo,含 SDL/ImGui) | 集中出现 |
| 离线工具(idl / makeproto / map_editor 代码生成器) | 集中出现 |

也就是说,**真正的运行时核心几乎全部依赖智能指针与 RAII 管理资源**,裸分配仅存在于非运行时的演示与离线工具中。这是该项目最值得肯定的工程素养之一——在一个 17 万行的 C++ 项目里保持核心层的内存纪律并不容易。

### 3.2 数据库访问层:安全性到位

- 提供 `escape()` 转义接口,并支持 `MYSQL_BIND` **参数化预处理查询**(`stmt_query`),具备 SQL 注入防护意识。
- MySQL 连接池用 `std::shared_mutex` + 信号量管理,Redis 连接析构时正确释放。

在游戏服务器这类对数据安全敏感的领域,默认走参数化查询是正确的工程选择。

### 3.3 工具基础设施

- **异步日志**:日志投递到独立的日志 actor,非阻塞,通过 actor 模型隔离实现线程安全,避免显式锁竞争。
- **序列化**:模板特化 + 折叠表达式,编译期类型检查,显式处理小端字节序。
- **行为树(AI)**:`shared_ptr`/`unique_ptr` 管理节点,黑板共享数据,无裸指针泄漏。
- **配置表**:CSV/JSON/XML 多格式支持,带哈希变更检测的热重载能力。

### 3.4 客观存在的质量风险

为保持客观,以下是代码评审中发现的真实风险点(均有明确代码依据):

1. **并发可见性靠约定**:actor 的关闭标志位 `m_release` 是裸 `bool` 而非 `std::atomic`,在无锁读取路径上存在编译器优化导致的可见性风险,建议原子化。
2. **状态机竞态窗口**:`actor_manage` 中 free→list→run→close 的状态转换在多线程下存在边界竞态,需要更强的同步保证或状态机收敛。
3. **连接对象所有权外逃**:网络层个别路径在锁外返回连接的原始指针/拷贝,理论上存在 use-after-free 风险,建议统一返回 `shared_ptr` 并在回调内校验存活。
4. **序列化无版本字段**:跨版本格式演化缺乏兼容保障,长期维护需补充。
5. **部分 C API 返回值未校验**:如 `mysql_init`/`mysql_options`,健壮性可加强。
6. **异常吞咽**:个别 catch-all(如析构中)掩盖异常类型,不利于排障。

这些大多属于"并发正确性更多依赖约定而非语言机制"这一类——在功能正确的前提下,缺少机器可验证的约束。它们是中大型 C++ 服务器项目的常见课题,**建议配合 ThreadSanitizer / AddressSanitizer 实跑验证**(项目已具备 Sanitizer 构建选项,基础设施齐备)。

> **代码质量评分 7.2**:核心层内存纪律与 DB 安全性是明确加分项;并发正确性的机制化保障是主要扣分项。

## 四、工程化(构建 / 依赖)—— 8.5 / 10

这是该框架综合素质最高的维度,达到了专业开源项目的工程标准。

### 4.1 构建系统

- **target-based CMake**:用 `INTERFACE` 库(`ngl_build_options`)集中管理编译选项、宏定义与链接依赖,而非全局变量污染,符合现代 CMake 最佳实践。
- **Unity Build**:默认启用、批量可配置,并对 protobuf 生成源码做了单独处理(每个 `.pb.cc` 独立编译单元),避免静态符号冲突——这是踩过坑后的成熟处理。
- **Sanitizer**:提供 AddressSanitizer + UndefinedBehaviorSanitizer 可选开关(Linux/Clang/GCC)。
- **强警告**:MSVC `/W4`、GCC/Clang `-Wall -Wextra -Wpedantic`,可配置。
- **跨平台**:Windows(MSVC)与 Linux(GCC)分别适配,编译输出目录统一到 `bin/<Config>`。
- **可选 mimalloc**:可接管全局 `new`/`delete`,面向高分配压力场景。

### 4.2 依赖管理

- **Conan 2** 管理全部第三方依赖,且**全部 pin 到具体小版本**(boost/1.86.0、protobuf/3.21.12、lua/5.4.6、mimalloc/2.2.4 等),构建可复现。
- 按平台条件依赖(Linux 下 libuuid,Windows 下 sdl/imgui)。
- 显式关闭不需要的依赖特性(如 behaviortree 的 Groot/SQLite),缩短编译时间。

依赖管理的规范度,是很多 C++ 项目最薄弱的环节,而本项目处理得相当干净。

### 4.3 持续集成与质量门禁

- **GitHub Actions** 多 workflow:Windows 构建、Linux 构建(Unity / 非 Unity 双验证)、clang-format 格式检查、手动测试触发。
- **Conan 缓存** key 设计合理(含编译器、C++ 标准、文件哈希),CI 提速。
- **SonarCloud** 质量门禁(README 徽章)。
- **GoogleTest** 11 个测试套件,覆盖 Actor 管理、网络、序列化、启动流程、运行时、工具链等核心模块。

### 4.4 待改进

- **CI 测试执行**:当前 CI 偏重"构建可过",自动化测试的执行闭环可进一步加强(让 11 套测试成为 PR 的强制门禁)。
- **覆盖率报告**:尚无覆盖率统计。
- **静态分析**:cppcheck 配置存在,但更宜接入 CI 并扩展到 Release 配置。
- **容器化**:框架的单镜像多角色设计非常适合容器化,可补充官方 Dockerfile 与编排示例。

> **工程化评分 8.5**:Conan 全 pin、target-based CMake、Unity Build、Sanitizer、双平台 CI 共同构成了生产级的构建基础设施,这是本项目最强的一环。

## 五、综合评价

### 5.1 这是一个什么水平的项目

`ngl_server` 是一个**工程底子扎实、设计成型**的中大型 C++ 游戏服务器框架,具备生产级框架的完整骨架:

- 在**架构**上,Actor 分层调度 + 单镜像多角色 + 配置驱动拓扑,是清晰且可扩展的设计;
- 在**工程化**上,Conan 全 pin、现代 CMake、Sanitizer、双平台 CI,达到了专业开源项目的标准;
- 在**代码质量**上,核心运行时的内存纪律与数据库安全性体现了成熟的工程素养;
- 在**现代 C++** 上,熟练运用 C++20 资源管理与模板元编程,并对 C++23 演进有清晰规划。

它的主要提升空间集中在**并发正确性的机制化保障**(从"靠约定"走向"靠类型与原子操作约束")、**协议层抽象的进一步收敛**,以及 **CI 测试闭环与可观测性**的补强。这些都是中大型 C++ 服务器项目共有的进阶课题,而非设计缺陷。

### 5.3 技术亮点清单(适合简历/面试展开)

- 设计并实现了基于 **Actor 模型的两层调度并发内核**,工作线程池与调度逻辑解耦,支持优先级抢占。
- 实现了 **TCP / WebSocket(WSS) / KCP 三协议统一网络栈**,基于 Boost.Asio 零拷贝发送 + 双缓冲。
- 设计了**单二进制多角色 + 配置驱动拓扑**的分布式部署模型,一套代码支撑 12 种节点类型与多区/跨服。

- 自研了**序列化、异步日志、数据库连接池(参数化查询)、Lua 绑定、行为树**等全套基础设施。
- 对语言演进有工程化把控能力:完成 **C++20 → C++23 升级的构建链路与 CI 准备**。
